Ansible is a cross-platform, agentless automation tool. It talks to managed nodes over
SSH (or WinRM on Windows), so there is nothing to install on the machines you manage.

<Callout title="Versions used in this guide">
  Ansible community package **14.5.0** · ansible-core **2.21.5** · **Python 3.12 or
  newer** on the control node · FQCN modules such as `ansible.builtin.package`
</Callout>

<Callout title="The control node needs a recent Python">
  ansible-core 2.21 requires **Python 3.12+** on the control node. The managed nodes only
  need Python 3.9 or newer — and Windows nodes are managed over WinRM with PowerShell, so
  they need no Python at all.
</Callout>

## System Requirements

### Control Node

- Linux, macOS or a WSL2 distribution (Windows is not supported as a control node)
- Python 3.12 or newer
- `ssh` and `git` available
- The ability to reach the managed nodes over SSH (port 22) or WinRM (port 5985/5986)

### Managed Nodes

- Linux with Python 3.9+
- Windows with PowerShell 3.0+ and the WinRM feature enabled
- SSH key-based authentication (strongly recommended)

    ```bash
    # Update the package index
    sudo apt update

    # Install the community package (includes ~300 collections)
    sudo apt install -y ansible

    # Verify
    ansible --version
    ```

    To install only the core engine and add the collections you actually need:

    ```bash
    sudo apt install -y ansible-core
    ```

    ### RHEL / CentOS / Rocky / Alma (dnf)

    ```bash
    # Enable the EPEL repository for the community packages
    sudo dnf install -y epel-release

    # Or install the full community package
    sudo dnf install -y ansible

    ansible --version
    ```

  <TabsContent value="macos">
    ### macOS (Homebrew)

    ```bash
    brew install ansible

    ansible --version
    ```
  </TabsContent>

  <TabsContent value="pip">
    ### pip in a virtual environment

    This is the recommended way to pin the version per project:

    ```bash
    # Create a virtual environment
    python3 -m venv ~/.venvs/ansible
    source ~/.venvs/ansible/bin/activate

    # Install the community package
    pip install --upgrade pip
    pip install 'ansible==14.5.0'

    ansible --version
    ```

    Pin the exact version in a `requirements.txt` so every machine and CI job installs the
    same build:

    ```bash
    ansible==14.5.0
    ```
  </TabsContent>

  <TabsContent value="windows">
    ### Windows (WSL2)

    Install WSL2 with a Linux distribution, then use the Debian or Ubuntu instructions
    inside it:

    ```bash
    wsl --install -d Ubuntu
    # Inside WSL
    sudo apt update && sudo apt install -y ansible
    ansible --version
    ```

## Project Layout

```bash
mkdir -p ~/ansible/{playbooks,roles,inventory,collections}
cd ~/ansible
```

```bash
# Create a requirements file for the collections you need
ansible-galaxy collection init
```

```yaml
# requirements.yml
collections:
  - name: community.general
    version: ">=10.0.0"
  - name: ansible.posix
    version: ">=1.5.0"
```

```bash
# Install the collections
ansible-galaxy collection install -r requirements.yml

# Update them later
ansible-galaxy collection install -r requirements.yml --upgrade
```

## Inventory

Create `inventory.ini`:

```ini
[webservers]
web1 ansible_host=192.168.1.10
web2 ansible_host=192.168.1.11

[dbservers]
db1 ansible_host=192.168.1.20

[all:vars]
ansible_user=deploy
ansible_ssh_private_key_file=~/.ssh/id_ed25519
```

Or use YAML, which is the format to prefer:

```yaml
# inventory.yaml
all:
  children:
    webservers:
      hosts:
        web1:
          ansible_host: 192.168.1.10
        web2:
          ansible_host: 192.168.1.11
    dbservers:
      hosts:
        db1:
          ansible_host: 192.168.1.20
  vars:
    ansible_user: deploy
    ansible_ssh_private_key_file: ~/.ssh/id_ed25519
```

## Configuration

Create `ansible.cfg` in the project root:

```ini
[defaults]
inventory = ./inventory.yaml
roles_path = ./roles
host_key_checking = True
stdout_callback = yaml
interpreter_python = auto_silent
retry_files_enabled = False

[ssh_connection]
pipelining = True
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
```

## Your First Playbook

Create `playbooks/install-nginx.yml`:

```yaml
---
- name: Install and start Nginx
  hosts: webservers
  become: true
  vars:
    nginx_packages:
      - nginx
      - curl

  tasks:
    - name: Update the package cache (Debian/Ubuntu)
      ansible.builtin.apt:
        update_cache: true
      when: ansible_os_family == "Debian"
      changed_when: false

    - name: Update the package cache (RHEL/CentOS)
      ansible.builtin.dnf:
        update_cache: true
      when: ansible_os_family == "RedHat"
      changed_when: false

    - name: Install the packages
      ansible.builtin.package:
        name: "{{ nginx_packages }}"
        state: present

    - name: Ensure Nginx is running and enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

```bash
# Test the connection
ansible webservers -m ping

# Validate the syntax
ansible-playbook playbooks/install-nginx.yml --syntax-check

# Preview the changes without applying them
ansible-playbook playbooks/install-nginx.yml --check --diff

# Run it
ansible-playbook playbooks/install-nginx.yml
```

<Callout title="Use fully qualified collection names">
  Write `ansible.builtin.package` instead of `package`. Short names only work when the
  collection is loaded implicitly, and the FQCN form is what `ansible-lint` expects.
</Callout>

## Handling Secrets with Ansible Vault

```bash
# Create an encrypted variables file
ansible-vault create secrets.yml

# Edit it
ansible-vault edit secrets.yml

# Encrypt an existing file
ansible-vault encrypt --output secrets.enc.yml vars.yml

# Use it in a playbook
ansible-playbook site.yml --ask-vault-pass
```

```yaml
# vars/vault.yml (encrypted)
db_password: "super-secret"
api_token: "another-secret"
```

```bash
# Use a password file in CI instead of an interactive prompt
ansible-playbook site.yml --vault-password-file .vault-password
```

## Execution Environments

Execution environments are containers that package Ansible and its dependencies, so a
pipeline always runs the same stack:

```bash
# Install the builder
pip install ansible-builder

# Build the image
ansible-builder build --file execution-environment.yml --tag my-ee:latest

# Run a playbook inside it
podman run -it --rm -v $(pwd):/z my-ee:latest ansible-playbook site.yml
```

```yaml
# execution-environment.yml
version: 3
images:
  base_image:
    name: registry.redhat.io/ubi9/ubi-minimal:latest
dependencies:
  galaxy: requirements.yml
  python: requirements.txt
  system: bindep.txt
```

## Troubleshooting

<Accordion type="single">
  <AccordionItem value="issue-1">
    <AccordionTrigger>
      SSH connection failures
    </AccordionTrigger>
    <AccordionContent>
      Test the connection outside Ansible first:
      ```bash
      ssh -v deploy@192.168.1.10
      ansible webservers -m ping -vvv
      ```
      The usual causes are an unreachable host, a key that is not in `authorized_keys`, or
      a `known_hosts` mismatch after the host was rebuilt. `ssh-keygen -R <host>` clears
      the stale key.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-2">
    <AccordionTrigger>
      "The module failed to execute successfully" or a missing Python error
    </AccordionTrigger>
    <AccordionContent>
      The managed node has no usable Python:
      ```bash
      # Check which interpreter Ansible picks
      ansible host -m setup -a "filter=ansible_python_version"

      # Install Python with the raw module
      ansible host -m raw -a "apt-get update && apt-get install -y python3"
      ```
      Set `interpreter_python = auto_silent` in `ansible.cfg` to fall back automatically.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-3">
    <AccordionTrigger>
      Permission errors when using become
    </AccordionTrigger>
    <AccordionContent>
      ```bash
      # Check the sudo rights of the remote user
      ansible host -m shell -a "sudo -l"

      # Provide the password from a vault variable
      ansible-playbook site.yml --become --become-password-file .sudo-password
      ```
      Prefer passwordless sudo for the deploy user over shipping a password around.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-4">
    <AccordionTrigger>
      The task runs but the change is not applied
    </AccordionTrigger>
    <AccordionContent>
      Modules report "ok" when they did not have to do anything. Check the diff:
      ```bash
      ansible-playbook site.yml --check --diff
      ```
      A common cause is a `when` condition that never matched, or a `changed_when` that
      hides the real result.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-5">
    <AccordionTrigger>
      Playbook is slow
    </AccordionTrigger>
    <AccordionContent>
      ```bash
      # Profile where the time goes
      ANSIBLE_CALLBACK_PROFILE_ENABLED=True ansible-playbook site.yml

      # Enable pipelining and ControlPersist in ansible.cfg
      ```
      A `forks` value above the default of 5 also helps on many hosts.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-6">
    <AccordionTrigger>
      Linting and syntax errors
    </AccordionTrigger>
    <AccordionContent>
      ```bash
      # Syntax check
      ansible-playbook site.yml --syntax-check

      # Lint with ansible-lint
      pip install ansible-lint
      ansible-lint playbooks/
      ```
      `ansible-lint` catches most issues before they reach a real host.
    </AccordionContent>
  </AccordionItem>
</Accordion>

## Best Practices

1. **Use ansible-core** and add only the collections you need — it keeps the control node
   small and the version pinned.
2. **Pin versions** in `requirements.yml` and commit the lock file.
3. **Use YAML inventory** and group hosts by role, not by team.
4. **Use FQCN module names** and run `ansible-lint` in CI.
5. **Keep secrets in Ansible Vault**, never in plain variables.
6. **Run with `--check --diff` first** on any change that touches a production system.
7. **Prefer idempotent modules** (`package`, `service`, `template`) over `shell` and
   `command`.
8. **Use `block`/`rescue`/`always`** for error handling instead of `ignore_errors`.
9. **Set `forks` and pipelining** to keep large fleets fast.
10. **Run in an execution environment** in CI for reproducible builds.
