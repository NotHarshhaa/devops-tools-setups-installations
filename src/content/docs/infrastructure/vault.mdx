Vault is a secrets management platform. It stores tokens, passwords, certificates and
encryption keys, and issues short-lived credentials to the applications that need them.

<Callout title="Versions used in this guide">
  Vault **2.2.0** (IBM Vault Community Edition) · KV v2 secrets engine ·
  Integrated Storage (Raft) for production · AppRole and AWS IAM authentication ·
  `max_token_header_size` listener option for the 2.x hardening
</Callout>

<Callout title="Vault 1.21.x is the previous line">
  Vault 2.x is the current major release. The 1.21.x line is still supported, and most
  breaking changes in 2.0 are internal to the SDKs and auth plugins — but plan your
  upgrade and read the release notes first.
</Callout>

## System Requirements

- A 64-bit operating system (Linux, macOS, Windows, FreeBSD)
- 2 GB RAM for a small deployment, 8 GB or more for a production cluster
- A persistent disk for the Raft data store
- TLS certificates for the listener in production
- Root/sudo privileges to install the system service

## Configuration

### Development

```bash
# Start a development server with an in-memory store
vault server -dev

# The root token is printed at startup
export VAULT_ADDR='http://127.0.0.1:8200'
export VAULT_TOKEN='<root-token-from-the-log>'
```

### Production (Integrated Storage / Raft)

Create `/etc/vault.d/vault.hcl`:

```hcl
ui = true

api_addr = "https://vault.example.com:8200"
cluster_address = "https://vault.example.com:8201"

# Integrated Storage
storage "raft" {
  path = "/opt/vault/data"
  node_id = "vault-node-1"

  retry_join {
    node_id = "vault-node-2"
    peer_addr = "https://vault-node-2.example.com:8201"
  }
}

listener "tcp" {
  address     = "0.0.0.0:8200"
  cluster_address = "0.0.0.0:8201"
  tls_cert_file   = "/etc/vault.d/cert.pem"
  tls_key_file    = "/etc/vault.d/key.pem"
  tls_client_ca_file = "/etc/vault.d/ca.pem"
  tls_min_version = "tls12"

  # Vault 2.x bounds the size of the token headers (default 8 KB)
  max_token_header_size = 8192
}

# Enable the audit device before you store anything
disable_mlock = true
```

```bash
# Create the data directory with the right ownership
sudo mkdir -p /opt/vault/data
sudo chown -R vault:vault /opt/vault
sudo chmod 750 /opt/vault

# Start the service
sudo systemctl enable --now vault
sudo systemctl status vault
sudo journalctl -u vault -f
```

## Initialising and Unsealing

```bash
# Initialise with 5 key shares and a threshold of 3
vault operator init -key-shares=5 -key-threshold=3

# Save the unseal keys and the root token somewhere safe
# Unseal with any 3 of the 5 keys
vault operator unseal <key1>
vault operator unseal <key2>
vault operator unseal <key3>

# Check the status
vault status

# Log in with the root token
vault login <root-token>
```

<Callout title="Never store the unseal keys next to Vault">
  The unseal keys are the master secret of your Vault. Keep them offline, in separate
  places, and use Shamir's secret sharing for the team. In production, use automatic
  unsealing with a cloud KMS (AWS KMS, GCP Cloud KMS, Azure Key Vault) or HSM.
</Callout>

### Automatic Unsealing

```hcl
seal "awskms" {
  region     = "eu-central-1"
  key_id     = "arn:aws:kms:eu-central-1:123456789012:key/abcd-1234"
  access_key = ""
  secret_key = ""
  iam_role_arn = "arn:aws:iam::123456789012:role/vault-unseal"
}
```

## Secrets Engines

```bash
# Enable the KV v2 engine (the default path is "secret")
vault secrets enable -path=secret kv-v2

# Check what is enabled
vault secrets list

# Write and read a secret
vault kv put secret/myapp/config username=myuser password=mypassword
vault kv get secret/myapp/config
vault kv get -format=json secret/myapp/config | jq -r '.data.data.password'

# Enable the AWS dynamic credentials engine
vault secrets enable aws
vault write aws/config/root \
  region=eu-central-1 \
  access_key=$AWS_ACCESS_KEY_ID \
  secret_key=$AWS_SECRET_ACCESS_KEY

# Issue short-lived credentials
vault read aws/creds/my-role
```

## Authentication

```bash
# Enable AppRole — designed for machine identities
vault auth enable approle

# Create a role
vault write auth/approle/role/my-role \
    secret_id_ttl=10m \
    token_num_uses=10 \
    token_ttl=20m \
    token_max_ttl=30m \
    secret_id_num_uses=40

# Fetch a role id and a secret id
vault read -field=role_id auth/approle/role/my-role/role-id
vault write -f -field=secret_id auth/approle/role/my-role/secret-id

# Log in
vault write auth/approle/login role_id=<role-id> secret_id=<secret-id>
```

```bash
# Enable AWS IAM authentication for EC2, EKS and ECS workloads
vault auth enable aws
vault write auth/aws/config \
    type=iam \
    role_arn="arn:aws:iam::123456789012:role/vault-auth"

vault write auth/aws/role/my-role \
    bound_iam_principal_arn="arn:aws:iam::123456789012:role/my-app" \
    policies=my-policy \
    ttl=1h
```

## Policies

Create `app-policy.hcl`:

```hcl
path "secret/data/myapp/*" {
  capabilities = ["read", "list"]
}

path "auth/approle/login" {
  capabilities = ["create", "update"]
}
```

```bash
vault policy write app-policy app-policy.hcl
```

## Audit Logging

Enable at least one audit device **before** you store any secrets — audit logs are the
only record of who accessed what.

```bash
# File audit device
vault audit enable file file_path=/var/log/vault/audit.log

# Syslog audit device
vault audit enable syslog facility=local tag=vault

# List the active devices
vault audit list
```

```bash
# Rotate the root token and create a scoped one instead
vault token create -policy=app-policy -ttl=1h -explicit-max-ttl=4h
```

## Upgrading

```bash
# 1. Back up the data directory
sudo systemctl stop vault
sudo tar -czf /var/backups/vault-$(date +%F).tar.gz -C /opt/vault data
sudo systemctl start vault

# 2. Upgrade the package
sudo apt update && sudo apt install --only-upgrade vault

# 3. Restart and check the seal status
sudo systemctl restart vault
vault status
```

## Troubleshooting

<Accordion type="single">
  <AccordionItem value="issue-1">
    <AccordionTrigger>
      The server will not start
    </AccordionTrigger>
    <AccordionContent>
      ```bash
      # Read the log
      sudo journalctl -u vault -n 100 --no-pager

      # Check the configuration
      sudo vault operator diagnose -format=json
      ```
      The most common causes are a wrong file path, a missing `node_id` in the Raft
      config, or a data directory that the `vault` user cannot write to.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-2">
    <AccordionTrigger>
      The server is sealed
    </AccordionTrigger>
    <AccordionContent>
      ```bash
      vault status
      # Unseal with the threshold number of keys
      vault operator unseal <key1>
      ```
      If the server was restarted, it seals again — that is the expected behaviour
      unless you configure automatic unsealing.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-3">
    <AccordionTrigger>
      "Error checking seal status: connection refused" or TLS errors
    </AccordionTrigger>
    <AccordionContent>
      ```bash
      export VAULT_ADDR='https://vault.example.com:8200'
      export VAULT_CACERT=/etc/vault.d/ca.pem

      # Or skip verification in a lab (never in production)
      export VAULT_SKIP_VERIFY=true
      ```
      Make sure `VAULT_ADDR` matches the `api_addr` in the configuration, including the
      scheme.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-4">
    <AccordionTrigger>
      Permission denied errors
    </AccordionTrigger>
    <AccordionContent>
      The token is missing the capability, or the policy path is wrong:
      ```bash
      # Check the token
      vault token lookup
      # Check the capabilities on a path
      vault token capabilities secret/data/myapp/config
      ```
      Note that KV v2 policies use the `secret/data/...` path, not `secret/...`.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-5">
    <AccordionTrigger>
      mlock errors
    </AccordionTrigger>
    <AccordionContent>
      Vault wants to lock memory and needs `CAP_IPC_LOCK`:
      ```bash
      # systemd override
      sudo systemctl edit vault
      ```
      ```ini
      [Service]
      AmbientCapabilities=CAP_IPC_LOCK
      CapabilityBoundingSet=CAP_IPC_LOCK
      ```
      Alternatively set `disable_mlock = true` and make sure swap is disabled.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-6">
    <AccordionTrigger>
      The Raft cluster will not form
    </AccordionTrigger>
    <AccordionContent>
      ```bash
      # Check the cluster membership
      vault operator raft list-peers

      # Check the logs for the gossip errors
      sudo journalctl -u vault -f | grep -i raft
      ```
      Verify that port 8201 is open between the nodes and that every node uses the same
      `cluster_name`.
    </AccordionContent>
  </AccordionItem>
</Accordion>

## Best Practices

1. **Use Integrated Storage (Raft)** for production instead of the file backend.
2. **Enable automatic unsealing** with a cloud KMS and never store unseal keys with the
   server.
3. **Enable audit devices before you store any secrets** and ship the logs off-host.
4. **Use short-lived, scoped tokens** — never hand out the root token to applications.
5. **Prefer dynamic credentials** over static secrets; Vault issues AWS, database and SSH
   credentials on demand.
6. **Run at least three nodes** in a cluster, spread across failure domains.
7. **Use TLS on the listener** and a `tls_min_version` of `tls12` or higher.
8. **Back up the Raft store** and test the restore regularly.
9. **Use the Vault Agent** to inject secrets into applications without them ever being
   written to disk.
