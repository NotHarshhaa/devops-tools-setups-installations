Packer builds identical machine images for multiple platforms from a single
configuration. One template, many clouds — with the same provisioners and the same
result everywhere.

<Callout title="Versions used in this guide">
  Packer **1.16.1** · HCL2 templates with `source` and `build` blocks ·
  `required_plugins` for plugin pinning · the `provenance` post-processor and
  `packer verify-attestation` for SLSA build attestations
</Callout>

## System Requirements

- A 64-bit operating system (Linux, macOS, Windows, FreeBSD)
- Packer is a single static binary — no runtime dependencies
- Credentials for the target platform (AWS, Azure, GCP, Proxmox, QEMU, …)
- For local builds: a hypervisor such as QEMU, VirtualBox, VMware or Hyper-V

## Verifying the Installation

```bash
# Version
packer version

# List the available plugins
packer plugins installed

# Format a template
packer fmt .

# Validate a template
packer validate .
```

## Your First Template

Create `template.pkr.hcl`:

```hcl
packer {
  required_plugins {
    amazon = {
      source  = "github.com/hashicorp/amazon"
      version = ">= 1.3.0"
    }
  }
}

variable "aws_region" {
  type    = string
  default = "eu-central-1"
}

variable "ami_name" {
  type    = string
  default = "app-base-{{timestamp}}"
}

source "amazon-ebs" "ubuntu" {
  region        = var.aws_region
  instance_type = "t3.micro"
  ami_name      = var.ami_name
  source_ami    = "ami-0abcdef1234567890" # Ubuntu 24.04 LTS
  ssh_username  = "ubuntu"
  ami_name_filter = "app-base-*"
  tags = {
    Name        = var.ami_name
    built_by    = "packer"
    build_date  = "{{timestamp}}"
  }
}

build {
  name    = "ubuntu-base"
  sources = ["source.amazon-ebs.ubuntu"]

  provisioner "shell" {
    inline = [
      "sudo apt-get update",
      "sudo apt-get install -y nginx",
      "sudo systemctl enable nginx",
    ]
  }

  provisioner "file" {
    source = "./nginx.conf"
    destination = "/tmp/nginx.conf"
  }

  post-processor "manifest" {
    output     = "manifest.json"
    strip_path = true
  }
}
```

```bash
# Install the plugins the template needs
packer init .

# Validate the template
packer validate .

# Build it
packer build .

# Build only one source, or exclude one
packer build -only="amazon-ebs.ubuntu" .
packer build -except="amazon-ebs" .
```

<Callout title="Pins belong in required_plugins">
  Declare every plugin with a version constraint and commit the generated
  `.packer.lock.hcl` file. Without it, a build can silently pick up a different plugin
  version and produce a different image.
</Callout>

## Building on Other Platforms

Packer uses the same template structure for every platform — only the `source` block
changes.

```hcl
# Azure
source "azure-arm" "ubuntu" {
  location          = "westeurope"
  vm_size           = "Standard_B1s"
  image_source_id   = "/subscriptions/.../sourceImage"
  ssh_username      = "packer"
  image_offer       = "0001-com-ubuntu-server-jammy"
  image_sku         = "22_04-lts-gen2"
}

# Google Cloud
source "googlecompute" "ubuntu" {
  project_id = "my-project"
  source_image_family = "ubuntu-2404-lts-amd64"
  image_name  = "app-base-{{timestamp}}"
  ssh_username = "packer"
  zone         = "europe-west4-a"
  machine_type = "e2-medium"
}
```

## Build Attestations (SLSA)

Packer 1.16 can emit and verify signed provenance for the images it builds, so consumers
can prove where an image came from:

```hcl
post-processor "provenance" {
  only = ["docker.*"]
  # Sign with a local PEM key
  sign = "./cosign.key"
  # ...or with a cloud KMS key
  # sign = "awskms:///alias/cosign"
}
```

```bash
# Verify an attestation
packer verify-attestation --path "pkg:docker/your-image@sha256:..." \
  --certificate "chain.pem" --key "cosign.key"
```

## Upgrading

```bash
# Upgrade the binary
sudo apt update && sudo apt install --only-upgrade packer

# Update the plugins
packer plugins update

# Check what is installed
packer plugins installed
```

## Troubleshooting

<Accordion type="single">
  <AccordionItem value="issue-1">
    <AccordionTrigger>
      "Plugin not found" or "Missing plugins" errors
    </AccordionTrigger>
    <AccordionContent>
      The template declares plugins that are not installed:
      ```bash
      packer init .          # install the required plugins
      packer plugins required .
      packer plugins installed
      ```
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-2">
    <AccordionTrigger>
      The build fails during the shell provisioner
    </AccordionTrigger>
    <AccordionContent>
      Scripts fail on the first non-zero exit code. Add error handling and check the
      output:
      ```hcl
      provisioner "shell" {
        inline = ["set -e", "sudo apt-get update"]
        expect_disconnect = true
      }
      ```
      Use `execute_command` to change the interpreter, for example `expect_disconnect`
      for Windows or a custom SSH command.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-3">
    <AccordionTrigger>
      Cloud credentials are not found
    </AccordionTrigger>
    <AccordionContent>
      Packer uses the standard provider SDK credential chain:
      ```bash
      # AWS
      export AWS_PROFILE=my-profile
      # or use a temporary token
      export AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... AWS_SESSION_TOKEN=...

      # Azure
      az login
      export ARM_CLIENT_ID=... ARM_CLIENT_SECRET=... ARM_TENANT_ID=...

      # GCP
      gcloud auth application-default login
      ```
      Never hardcode credentials in the template.
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-4">
    <AccordionTrigger>
      The build is slow
    </AccordionTrigger>
    <AccordionContent>
      Packer boots a machine, provisions it and shuts it down for every build. Reduce the
      work:
      - Use a shared base AMI with the common packages already installed
      - Bake configuration with `ansible-provisioner` and a local playbook instead of
        many `shell` steps
      - Use `-on-error=ask` to inspect a failed build interactively
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-5">
    <AccordionTrigger>
      The image already exists
    </AccordionTrigger>
    <AccordionContent>
      Most builders refuse to overwrite an existing artefact. Either make the name unique
      with `{{timestamp}}`, or clean up the old image first:
      ```bash
      packer build -var "ami_name=app-base-v2" .
      ```
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="issue-6">
    <AccordionTrigger>
      The template does not validate
    </AccordionTrigger>
    <AccordionContent>
      ```bash
      # Format it and validate again
      packer fmt -check -diff .
      packer validate .
      ```
      Validation only checks the template — it does not contact the cloud provider, so a
      template can validate and still fail at build time.
    </AccordionContent>
  </AccordionItem>
</Accordion>

## Best Practices

1. **Declare and pin plugins** in `required_plugins`, and commit `.packer.lock.hcl`.
2. **Version your images** — `{{timestamp}}` or a semantic version, never `latest`.
3. **Build one base image and layer on top** instead of rebuilding everything.
4. **Use `manifest` post-processors** so you know which artefact came from which build.
5. **Produce provenance attestations** for images you publish.
6. **Keep templates free of secrets** — use environment variables or a secrets manager.
7. **Run `packer validate` and `packer fmt -check` in CI** before every build.
8. **Tag images with the source commit** so you can trace an image back to the code.
